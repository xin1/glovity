# 协议一致性说明（实现 vs `03_串口协议规范_v1.0.md`）

> 交付要求（任务书 §3.3）：若实现过程中发现协议需要修订，**必须**同步更新协议文档版本号、
> 列出变更点，并回传说明。
>
> **结论：帧格式、命令码、错误码、事件、Profile 布局全部按 v1.0 实现，未做不兼容改动，
> 因此帧头 `VER` 仍为 `0x01`。** 下面列出实现过程中发现并处理的三处**文档内部不一致**
> 与两处**澄清**。全部处理都遵循协议 §14 的兼容规则（"同一命令的载荷只能在**尾部追加**
> 可选字段；已发布字段的语义/长度不可变"）。

## 2. 发现并处理的文档不一致

### 2.1 `BUS_PROBE` 应答长度：§9.2 的字段表是 11 字节，正文写"共 12 字节"

**位置**：`03_串口协议规范_v1.0.md` §9.2 `0x10 BUS_PROBE`。

逐字段相加是 `1+1+1+4+1+1+1+1 = 11` 字节，但同一段末尾写"共 12 字节"。

**处理**（兼容、不改已发布字段）：

* 前 11 字节**严格按字段表**排列，语义与顺序不变；
* 在**尾部追加**第 12 字节 `probe_speed_ok`（`1` = 400 kHz 下也确认通信正常，
  `0` = 只能跑 100 kHz）。这既补齐了文档声明的 12 字节，又给上位机提供了一个
  判断"上游上拉是否充足（硬件问题 V-1）"的直接依据。
* 上位机 `codec.BusProbeResp.decode()` 解前 11 字节，**容忍更长**的应答（协议 §14 要求）；
  `probe_speed_ok` 作为可选字段读取。

**给协议文档的建议**：把"共 12 字节"改为"共 11 字节（v1.0 实现追加可选的
`probe_speed_ok`，共 12 字节）"。

### 2.2 波形库可用容量的两种说法互相矛盾

**位置**：`02_AW8623X寄存器与模式参考.md` §5 说"以 `BASE_ADDR = 0x0800` 为例，波形库可用空间
约 `0x0800` 字节（2 kB）"；同一节的组库算法却是 `start = BASE_ADDR + offset`（向上生长）；
`03` 文档附录 D 第 12 条则明确要求"按**波形库在 `BASE_ADDR` 之上**、RTP FIFO 在其下理解"。

SRAM 共 3 kB（`0x000`~`0xBFF`），`BASE_ADDR = 0x800`：

| 理解 | 波形库可用 | 与算法是否自洽 | 与 FIFO 默认值是否自洽 |
|---|---|---|---|
| 库在 BASE_ADDR **之上**（附录 D 的理解，也是组库算法） | **1024 字节** | ✅ | ✅（`FIFO_AE=512`/`FIFO_AF=1536` 都 < 2048，落在下方空间） |
| 库在 BASE_ADDR **之下**（§5 那句"2 kB"） | 2048 字节 | ❌ 与 `BASE_ADDR + offset` 矛盾 | ✅ |

**处理**：以**组库算法 + 附录 D 第 12 条**为准，实现为"库在 `BASE_ADDR` 之上"，
因此 `WAVE_BEGIN` 回报的 `max_total_samples = 1024 − 1 − 4×N`。

两侧的同一套公式（`firmware/main/wave_codec.c` 与上位机 `waveform.editor_model.sram_budget`）：

```
可用字节数 avail = 3072 − base_addr          # base_addr = 0x0800 → 1024
max_total_samples = avail − 1 − 4 × N
已用 = 1 + 4 × N + Σlen   （必须 ≤ avail）
```

> ⚠️ **联调时必须用真实芯片读写验证**（协议附录 D 第 12 条的原文要求）：
> 用 `WAVE_COMMIT` + `WAVE_READBACK` 实测确认地址表与数据位置。若实测发现库确实在
> `BASE_ADDR` 之下，只需改 `wave_lib_avail_bytes()` 一处，协议与线上格式不变。

**给协议文档的建议**：修正 §5 的"约 2 kB"为"约 1 kB（`BASE_ADDR` 之上的字节数）"，
或明确写成"波形库在 `BASE_ADDR` 之下，容量 2 kB"，二选一，消除歧义。

### 2.3 `SET_PROFILE` 校验失败时的应答形式

**位置**：`03` 文档 §9.7：`← result(1) first_bad_field(1)`；
同段又写"字段越界时也可直接返回 `ERR_BAD_PARAM` 并在说明文本里给出字段名（推荐两者都做）"。

**问题**：一个 `SEQ` 的请求只能对应**一个**应答帧。若先回 `result=1, first_bad_field=off`
再回一个错误应答，上位机的请求-应答匹配会错乱（协议 §5 要求按 `SEQ` 一一匹配）。

**处理**：**只回一个错误应答**，把字段名与偏移都放进说明文本，例如：

```
FLAGS = 0x05 (RESPONSE|ERROR), CMD = 0x50,
payload = 03 "Profile 字段 36（偏移）被拒：drv1_lvl（7 位字段） 超出范围 0..127，实际 128"
```

`payload[0]` 是 `ERR_BAD_PARAM`。上位机 `DeviceError.text` 会完整透传到界面。

**给协议文档的建议**：把"推荐两者都做"改为"二选一：优先用错误应答并把字段偏移写进说明文本"。

## 3. 两处澄清（文档未明说，实现按最安全的方式处理）

### 3.1 TRIG 硬触发的 `started_mask` 补齐

协议 §9.6 已说明：`chan_mask` 含 CH5/6/7 时三者必然一起动，固件应把三位补齐后上报。
**实现**：`svc_play_expand_shared()` 在任何硬触发路径（`TRIG_PULSE` / `TRIG_LEVEL` /
`TRIG_PATTERN`）上先做补齐，再按"真正启动了哪些通道"回填 `started_mask`
（只统计**在线且未忙**的通道）。同时发一条 `EVT_LOG` 说明联动原因。

### 3.2 播放安全的"超时上界"与"立即停止"双保险

协议 §11.1 要求 `TRG1_STOP`/`TRG1_BRK` 强制为 1 且写后回读校验。**实现**额外做了两件事：

1. 硬触发脉冲串的通道一律上安全计时器（`period_ms × count + 500 ms`，并夹到
   `play_timeout_ms × 4` 以内），保证"触发后无人看管"也会自己停；
2. `TRIG_PARK` 与 `STOP` 都**同时写** `0x08` 的 `STOP_MODE` 位作为第二道手段，
   即使某个位被意外改写也还有一条路能停下来。

## 4. 未改动的部分（逐条确认）

| 项 | 结论 |
|---|---|
| 帧格式（SOF/VER/FLAGS/SEQ/CMD/CHAN/LEN/CRC16） | 逐字节按 §3 实现 |
| CRC16-CCITT-FALSE（poly 0x1021 / init 0xFFFF / 无反射 / 自检 0x29B1） | 按 §3.1 实现并双侧自检 |
| 解析器行为（垃圾字节 / VER 错 / LEN 超限 / CRC 错 / 粘包 / 断包） | 按 §3.2 实现，逐条有单测 |
| 命令码与错误码表 | 全部按 §8 / §6.1 实现，一个不缺 |
| 事件码与载荷 | 全部按 §10 实现 |
| Profile 64 字节布局与偏移 | 按附录 B 实现，固件/上位机/单测三处同一份规则 |
| 能力位 `caps` | 按 §9.1 的"本板期望值"实现 |
| `MORE` 位 | v1.0 设备**不置位**；上位机收到会记为协议违例并高亮 |
| `NORESP` | 固件不回应答；出错走 `EVT_ERROR` |
| 单帧一次写出、二进制模式无裸文本 | 已实现（`PROTO_ALLOW_RAW_LOG` 默认 0） |
